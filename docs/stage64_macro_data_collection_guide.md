# Stage64 Macro-Regime Data Collection Guide

## Purpose

This guide defines how to collect the missing Stage64 macro-regime source files before any validation scan. It follows the Stage64D3 acquisition and lag manifest.

No paper order, paper-live, live, EA promotion, or historical validation scan is allowed by this toolkit.

## Why this toolkit exists

Earlier project stages used GitHub Actions and downloaded artifacts for blocked regional access. The same operational method is retained, but the Stage64 macro-regime schema is stricter because each file must carry lag-safe availability fields such as `available_after_utc`, `release_time_utc`, or `release_date_utc`.

Old Stage31/FRED artifacts can be used as raw reference, but they are not directly sufficient unless they are converted to the Stage64 columns.

## Files produced or expected

### Auto-fetchable P0/P1 files

These can be generated by GitHub Actions with `tools/stage64_macro_data_collect.py`:

```text
data/macro_regime/raw/gold_d1_ohlc_2011_present.csv
data/macro_regime/raw/dxy_daily_2011_present.csv
data/macro_regime/raw/real_yield_or_proxy_daily_2011_present.csv
data/macro_regime/raw/vix_daily_2011_present.csv
```

### Manual or semi-manual files

These require official/manual acquisition because blind scraping is not reliable enough for lag-safe validation:

```text
data/macro_regime/raw/gold_etf_holdings_or_flows.csv
data/macro_regime/raw/central_bank_gold_demand_monthly_quarterly.csv
data/macro_regime/raw/macro_event_calendar_archive.csv
```

## GitHub Actions acquisition method

1. Push this toolkit.
2. Open GitHub Actions.
3. Run workflow: `Stage64 Macro Regime Data Acquisition`.
4. Use these inputs:

```text
start_date = 2011-01-01
offline_template_only = 0
allow_fred_graph_fallback = 1
```

5. If a `FRED_API_KEY` repository secret exists, the script uses FRED API. If not, it can use the FRED graph CSV fallback for FRED series.
6. Download artifact named like:

```text
stage64-macro-regime-data-<run_number>.zip
```

7. Install locally:

```bash
cd /Users/vahid/Desktop/xauusd-trader
python3 tools/stage64_install_macro_data_artifact.py ~/Downloads/stage64-macro-regime-data-<run_number>.zip --root .
```

8. Run preflight:

```bash
python3 app/stage64d4_source_file_import_preflight.py \
  --root . \
  --config configs/stage64d4_source_file_import_preflight.json \
  --out reports/stage64d4_source_file_import_preflight
```

## Manual file schemas

### gold_etf_holdings_or_flows.csv

```text
date_utc,etf_id,holdings_tonnes_or_flow,source,release_time_utc,available_after_utc
```

Minimum recommended source: GLD/major gold ETF official holdings archive or a provider export with a documented release convention. Join rule must be next session after publication.

### central_bank_gold_demand_monthly_quarterly.csv

```text
period_start,period_end,demand_value,unit,source,release_date_utc,available_after_utc
```

Minimum recommended source: World Gold Council or official central-bank/gold-reserve series with documented publication lag. It must be used only as slow regime prior, not timing.

### macro_event_calendar_archive.csv

```text
scheduled_time_utc,event_type,importance,country,known_before_event,source,available_after_utc
```

If a historical known-before-event archive cannot be acquired, this feature must be excluded from historical validation and used forward-only.

## Reusing old project files

Relevant old methods from the project history:

- Stage31/FRED workflow and artifact method: old FRED exogenous series can be reused as raw source reference.
- Stage38F/SPDR GLD loader design: useful for ETF holdings/flow ingestion ideas, but Stage64 requires the new `release_time_utc` and `available_after_utc` fields.
- Existing `data/exogenous/*.csv`: useful as coverage reference, but insufficient for Stage64 because history starts around 2022 and lag columns are not complete.

Do not copy old files directly into Stage64 raw paths unless they are normalized to the exact Stage64 schema.

## Acceptance before validation

At minimum, before any reduced-scope validation is even discussed:

```text
P0 files exist
P0 files start at or before 2011-01-01
P0 files have no duplicate primary keys
P0 files have parseable available_after_utc
Stage64D4 preflight passes P0
Stage64D is rerun and explicitly reports readiness for selected scope
```
